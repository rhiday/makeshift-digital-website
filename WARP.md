# WARP.md

This file provides guidance to WARP (warp.dev) when working with code in this repository.

## Overview

This repository is a static site export from Webflow for the Makeshift Digital website. There is no build pipeline, package manager config, or automated test suite; the code is plain HTML, CSS, JS, and static assets.

Key characteristics:
- Multiple top-level HTML documents (`index.html`, `portfolio.html`, `agencies.html`, case-study detail pages, error pages like `404.html`/`401.html`).
- Stylesheets in `css/` (`normalize.css`, `webflow.css`, and project-specific `makeshiftdigital.webflow.css`).
- Webflow runtime and interaction logic in `js/webflow.js`, along with additional inline scripts in `index.html`.
- Static assets in `images/` and `fonts/`.
- Third-party tracking and analytics injected directly into `index.html` (Microsoft Clarity, Google Analytics `gtag.js`).

Because this is an export, some behaviors (e.g., CMS collections, Webflow interactions) are driven by data attributes and scripts generated by Webflow rather than hand-written application code.

## Common commands

There is no build, lint, or test tooling defined in this repo (no `package.json`, no task runners). Development is done directly against the static files. The most useful commands are for serving the site locally.

### Serve the site locally

From the repository root, you can serve the static files with Python’s built-in HTTP server:

```bash path=null start=null
python3 -m http.server 8000
```

Then open `http://localhost:8000/` in a browser to view `index.html`. Other pages (e.g. `portfolio.html`) can be reached via their paths (`http://localhost:8000/portfolio.html`).

If the environment has Node.js available, an alternative is:

```bash path=null start=null
npx serve .
```

### Tests and linting

- **Automated tests:** There is no test framework or test runner configured in this repository. Any “single test” or regression checks must be implemented manually in the browser or by adding new tooling.
- **Linting/formatting:** No HTML/CSS/JS linters or formatters are configured. If needed, add them explicitly (e.g., via a new `package.json`) rather than assuming existing scripts.

## High-level structure and architecture

### HTML documents

- `index.html` is the main landing page. It wires up:
  - Global navigation and footer.
  - Sections for hero content, client logos, featured work (links to case-study HTML files), services, testimonials, and a contact form.
  - Tracking/analytics scripts and some inline CSS tweaks for scrollbars, frames, cursor blinking, and marquee-like image behavior.
- Additional HTML files (`portfolio.html`, `agencies.html`, various `how-*.html` case-study pages, `style-guide.html`, `webflow.html`, `untitled.html`) follow the same Webflow-export structure: a `<head>` with shared CSS/JS includes and a `<body>` built from Webflow components.

Most layout and behavior in these pages is declaratively encoded via `class` names and `data-w-*` attributes that Webflow’s runtime interprets.

### Styling (`css/`)

- `css/normalize.css` provides cross-browser normalization.
- `css/webflow.css` contains Webflow’s base styles and component primitives.
- `css/makeshiftdigital.webflow.css` contains project-specific classes and overrides for this site.

When changing styling, prefer editing `makeshiftdigital.webflow.css` or the original Webflow project and re-exporting, rather than modifying `webflow.css` directly (which is generated and may be overwritten on re-export).

### JavaScript (`js/webflow.js` and inline scripts)

- `js/webflow.js` is the large Webflow-generated runtime bundle. It includes:
  - The core Webflow interaction engine (scroll/hover animations, nav behaviors, etc.).
  - A bundled animation/runtime stack (e.g., Lottie and helpers) used by elements configured in Webflow.
  - Utility and polyfill code to support Webflow features across browsers.
- `index.html` also includes inline scripts that:
  - Load Google Web Fonts and set up basic feature-detection classes on `<html>`.
  - Initialize Microsoft Clarity and Google Analytics tracking.
  - Implement a simple text-rotation effect for elements with the `.dynamic-text` class.
  - Override the default Webflow form submission for the main contact form to POST to FormSubmit and toggle success/error messages.

When editing behavior:
- Prefer adding small, self-contained inline scripts or a new JS file rather than modifying the large `webflow.js` bundle (which is generated and hard to maintain).
- Be aware that many interactions are configured visually in Webflow; editing the exported JS directly may be overwritten on the next export.

### Assets (`images/` and `fonts/`)

- `images/` contains all hero/portfolio screenshots, client logos, icons, and favicons referenced throughout the HTML.
- `fonts/` holds local font files (Inter and JetBrains Mono variants) used by the typography system.

Paths to these assets are hard-coded in the HTML and CSS; if you rename or move files, update all corresponding references.

## Integration notes

- **Contact form:** The main contact form in `index.html` posts to FormSubmit via the `action` attribute (`https://formsubmit.co/YOUR_EMAIL@example.com`) and is wrapped with a custom `fetch`-based handler that shows/hides `.rl-success-message-2-2` and `.rl-error-message-2-2`. If integrating with a real backend or changing the email target, update both the form `action` and confirm that the success/error elements and IDs remain consistent.
- **Analytics:** Microsoft Clarity and Google Analytics are initialized in `<head>`. If future changes involve privacy, consent management, or cookie banners, they will need to coordinate with these scripts.

## How future agents should work in this repo

- Do not assume any Node/Python/CLI-based build, linting, or test commands exist; introduce tooling explicitly if required by the user.
- Treat `webflow.js` and `webflow.css` as generated artifacts; prefer non-destructive changes (e.g. new CSS rules in the project-specific CSS file or small, separate JS snippets).
- When adding functionality that would normally involve dynamic backends (forms, lead capture, etc.), keep in mind that this is a static deployment and rely on service integrations (like FormSubmit) or clearly surface the need for backend changes outside this repo.
- When adding new sections or elements, prefer reusing existing layout and component patterns (e.g. cards, grids, CTAs, testimonials) by copying existing HTML structures and updating only content (text, images, links).
- Avoid renaming or removing Webflow-generated classes (`w-*`), `data-w-*` attributes, and `w-node-*` IDs unless intentionally taking over that component’s layout/behavior; these are wired into `webflow.css` and `webflow.js`.
- Prefer adding new semantic or utility classes on top of existing ones and define styles in `css/makeshiftdigital.webflow.css` rather than modifying `webflow.css`.
- Keep DOM structure for complex components (navbars, dropdowns, forms, grids) aligned with the original Webflow export; move or duplicate whole blocks instead of deeply restructuring them.
